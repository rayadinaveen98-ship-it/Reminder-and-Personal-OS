# Native Notification Preview — Android and iOS

**Date:** 2026-10-22
**Scope:** Single native local reminder test on each platform.
**Stage:** Source committed, CI build/device verification pending.

## Scope

This is a focused native-system feasibility harness rather than the final Reminder and Personal OS. The Android Activity and SwiftUI iOS screen each request permission, schedule one notification approximately 60 seconds ahead, and can cancel the test. They do not track task completion, store arbitrary reminders or perform analytics. They use native scheduling, not in-app timers.

## Android

- Android AlarmManager schedules the test using setExactAndAllowWhileIdle when allowed, or setAndAllowWhileIdle as an approximate fallback when exact-alarm special access is unavailable.
- Android 13+ POST_NOTIFICATIONS permission is requested before scheduling a visible alert.
- A manifest BroadcastReceiver handles the alarm callback and posts a channel notification. The callback never marks a task complete.
- A single stored future deadline in SharedPreferences is re-registered on Activity resume and eligible restart/time-change broadcasts. This is preview-only state, not production transactional persistence.
- The UI shows capability state, the next due time, an exact alarm settings shortcut and cancellation.
- Source path: androidApp. Build command: gradle :androidApp:assembleDebug.
- Build artifact after successful CI: androidApp-debug.apk (unsigned release? This is a debug-signed build only, not a release package).

## iOS

- SwiftUI test app requests native UserNotifications alert/badge/sound permission.
- UNUserNotificationCenter schedules a one-shot UNTimeIntervalNotificationTrigger, with stable request identifier.
- Notification delegate requests foreground banner/sound presentation.
- Cancellation requests removal of pending and delivered notifications.
- No background timer, unsupported Focus override, or implicit Done outcome.
- Sources under iosApp; project generated by XcodeGen. A simulator build is not a signed phone install / TestFlight IPA.

## Quality and limitations

1. One fixed demo reminder only per platform. The full app still needs multi-reminder storage, schedule identity, occurrence history and transactionally reliable reconciliation.
2. Android SharedPreferences state is intentionally a primitive test aid; it must not be treated as a production scheduling database.
3. Android permission eligibility, OEM battery policies and iOS Focus and alert settings mean delivery timing cannot be universally guaranteed.
4. App background, swipe-away, reboot, permission revocation, power-off, cancellation and exact-vs-inexact timing need physical-device evidence.
5. iOS SwiftUI preview is not connected to KMP shared business logic yet; native scheduling boundaries are being validated first.
6. Debug builds, simulator builds and compilation are not proof of end-to-end reminder reliability.
